문제 1 해설 — Union-Find

핵심 아이디어: 각 노드의 대표(루트)를 찾는 find와 두 집합을 합치는 union 연산으로 그래프 연결성을 추적. 경로 압축과 랭크/사이즈 기반 합치기를 적용하면 거의 O(1) 시간 복잡도 (정확히는 역 아커만 함수 α(n)).

시간 복잡도: O((N + M) · α(N)) ≈ O(N + M)
공간 복잡도: O(N)

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n  # 그룹 크기

    def find(self, x):
        # 경로 압축
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False
        # 사이즈 기반 합치기: 작은 그룹을 큰 그룹에 붙임
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        return True


def solve(N, edges):
    uf = UnionFind(N)
    for a, b in edges:
        uf.union(a, b)
    # 루트별 그룹 크기 집계
    roots = {uf.find(i) for i in range(N)}
    max_size = max(uf.size[r] for r in roots)
    return (len(roots), max_size)


# 테스트
print(solve(7, [(0,1), (1,2), (3,4), (5,6)]))  # (3, 3)

다른 접근: BFS/DFS로 연결 컴포넌트 탐색해도 O(N+M)이지만, 동적으로 간선이 추가되는 상황(스트리밍)에서는 Union-Find가 압도적으로 유리. 또한 Union-Find는 쿼리당 즉시 응답이 가능하지만 BFS는 매번 전체 탐색이 필요.

문제 2 해설 — Copy-on-Write

동작 원리: fork() 호출 시 커널은 자식에게 메모리를 즉시 복사하지 않고, 부모와 동일한 물리 페이지를 가리키는 페이지 테이블을 만든 뒤 모든 페이지를 읽기 전용(read-only)으로 마킹한다. 부모나 자식이 페이지에 쓰기를 시도하면 페이지 폴트가 발생하고, 그때서야 커널이 해당 페이지를 복사해 쓰기를 시도한 프로세스에게 자기만의 사본을 준다.

왜 필요한가:

  • 성능: fork() 직후 대부분의 자식 프로세스는 exec()을 호출하므로(특히 셸에서), 부모 메모리를 통째로 복사하는 것은 낭비. exec()는 어차피 새 프로그램 이미지로 덮어쓰기 때문.
  • 메모리 효율: 부모-자식이 읽기만 한다면 영원히 페이지 공유 가능.

실제 복사가 일어나는 시점: 어느 쪽이든 쓰기를 시도하는 페이지에 한해, 페이지 단위(보통 4KB)로 복사. 변수 하나만 바뀌어도 그 페이지 전체가 복사됨.

주의할 점: Python 등 GC 언어의 reference count는 객체 헤더의 카운터를 매번 증가시키므로 fork() 후 부모 객체를 단순히 읽기만 해도 CoW가 발동되어 메모리가 분리됨. (uWSGI, Gunicorn 같은 prefork 모델의 메모리 폭증 원인)

문제 3 해설 — MVCC

락 기반 vs MVCC: 락 기반은 읽기-쓰기, 쓰기-쓰기 충돌을 락 획득 대기로 처리 → 동시성 저하. MVCC는 데이터의 여러 버전을 보관해 쓰기는 새 버전을 만들고, 읽기는 트랜잭션 시작 시점의 일관된 스냅샷에서 적절한 버전을 본다 → 읽기는 절대 쓰기를 막지 않음, 쓰기도 읽기를 막지 않음.

가시성(Visibility): 각 행 버전에는 생성 트랜잭션 ID(xmin)와 삭제 트랜잭션 ID(xmax)가 기록됨. 현재 트랜잭션의 ID, 활성 트랜잭션 목록, 격리 수준에 따라 어느 버전이 "보이는지" 결정.

  • PostgreSQL: 각 행이 새 위치에 새 버전으로 기록(in-place update X). 구버전은 VACUUM이 정리.
  • MySQL InnoDB: 클러스터드 인덱스는 in-place 업데이트, 이전 버전은 undo log에 저장. 읽기 시 undo log를 거슬러 올라가 적절한 버전 재구성.

단점:

  • 구버전 정리 비용 (PG의 VACUUM, MySQL의 purge thread) — 게을리하면 테이블 비대화(bloat) 발생
  • 장기 트랜잭션은 오래된 스냅샷을 유지시켜 모든 구버전을 살아있게 만듦 (PG에서 특히 치명적)
  • Phantom read 같은 쓰기 충돌은 여전히 격리 수준별로 별도 처리 필요 (PG: Serializable Snapshot Isolation, MySQL: Next-Key Lock)

문제 4 해설 — SSRF

취약점: 사용자 제어 URL을 검증 없이 서버가 직접 요청 → Server-Side Request Forgery (SSRF). 공격자는 외부 URL이 아닌 내부망/loopback/메타데이터 서비스를 노려 정보를 탈취하거나 내부 시스템과 상호작용.

공격 페이로드 예시:

  • http://169.254.169.254/latest/meta-data/iam/security-credentials/ — AWS IMDS에서 IAM 자격증명 탈취
  • http://localhost:6379/ — 내부 Redis 접근
  • file:///etc/passwd — 파일 스킴으로 로컬 파일 읽기
  • http://attacker.com/redirect → 302로 내부 IP로 리다이렉트 (우회 기법)

방어 기법:

  1. 스킴 화이트리스트: http/https만 허용. file/gopher/dict 등 차단.
  2. DNS 해석 후 IP 검증: URL의 호스트명을 resolve한 뒤, 결과 IP가 사설 대역(RFC 1918: 10/8, 172.16/12, 192.168/16), 루프백(127/8), 링크로컬(169.254/16) 등이면 거부. DNS rebinding 방지를 위해 resolve한 IP로 직접 연결.
  3. 리다이렉트 비활성화 또는 재검증: allow_redirects=False, 또는 매 리다이렉트마다 IP 화이트리스트 재검사.
  4. (추가) AWS 환경이라면 IMDSv2 강제: 토큰 기반 세션 인증으로 단순 GET SSRF 차단.

문제 5 해설 — DNSSEC

위협 모델: DNS 응답 위조(스푸핑), 캐시 포이즈닝, MITM. 기존 DNS는 무결성·인증 없는 평문 UDP라 응답을 신뢰할 수 없음.

주요 레코드:

  • DNSKEY: 도메인의 공개키. ZSK(Zone Signing Key)와 KSK(Key Signing Key)로 나뉨.
  • RRSIG: 각 레코드 세트(RRset)에 대한 ZSK 서명.
  • DS (Delegation Signer): 부모 존이 자식 존의 KSK 해시를 저장 — 위임 체인의 핵심.

검증 과정 (Chain of Trust):

  1. 리졸버는 루트의 KSK 공개키(trust anchor)를 신뢰점으로 미리 보유.
  2. example.com 조회 시, 루트 → .com 위임 DS 레코드의 RRSIG를 루트 ZSK로 검증 (그 ZSK는 다시 루트 KSK로 검증).
  3. .com의 KSK → ZSK → example.com의 DS로 위임 검증.
  4. 최종적으로 example.com의 A 레코드 RRSIG를 ZSK로 검증.
  5. 한 단계라도 실패하면 SERVFAIL 반환 — 위변조된 응답은 거부됨.

실무 한계: 배포율이 낮음(Top 도메인의 30% 미만), 키 롤오버 운영 부담, NSEC/NSEC3로 인한 존 워킹(zone walking) 가능성 등.

문제 6 해설 — PKI 인증서 폐기

폐기 사유 예시:

  • 개인키 유출 또는 유출 의심 (KeyCompromise)
  • 인증서 발급 정보 변경 (소속 변경, 도메인 양도)
  • CA의 발급 실수 / 부정 발급 발견
  • 알고리즘 약화 (예: SHA-1 서명 인증서 폐기)

CRL (Certificate Revocation List): CA가 주기적으로 발행하는 폐기 인증서 목록. 클라이언트가 CRL Distribution Point에서 다운로드해 캐싱 후 사용.
단점: 파일이 점점 커짐, 갱신 주기(보통 24h~7d) 동안 stale 가능, 매번 전체 다운로드 비용.

OCSP (Online Certificate Status Protocol): 클라이언트가 CA의 OCSP responder에 특정 인증서 시리얼만 질의. 실시간성 우수, 트래픽 적음.
단점: 클라이언트가 어느 사이트에 접속하는지 OCSP responder가 알게 됨 (개인정보 누출), responder 가용성에 TLS 핸드셰이크 의존.

OCSP Stapling (RFC 6066): 서버가 미리 OCSP responder에서 자기 인증서의 서명된 응답을 받아두고, TLS 핸드셰이크 중 Certificate Status 확장으로 클라이언트에게 함께 제공.

  • 클라이언트가 별도로 OCSP responder에 질의하지 않음 → 프라이버시 보호
  • OCSP 응답에 CA 서명이 있어 서버가 위조 불가
  • 응답에 timestamp가 있어 replay 방지

추가 키워드: Must-Staple (인증서 확장으로 stapling 의무화), CT (Certificate Transparency) 로그, Short-lived 인증서로 폐기 의존도 축소 트렌드.
