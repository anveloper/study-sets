문제 1. 구간 합 가중치 누적 후 최댓값

난이도: 중  차분 배열  누적합

길이 N인 정수 배열 A가 모두 0으로 초기화되어 있다. 이후 Q개의 쿼리 (l, r, v)가 주어진다. 각 쿼리는 인덱스 l부터 r까지 모든 원소에 정수 v를 더한다 (인덱스는 1부터 시작). 모든 쿼리를 적용한 후 배열 A에서 가장 큰 원소의 값을 출력하라.

입력
첫 줄에 N, Q가 공백으로 주어진다.
이어지는 Q개의 줄에 각각 l r v가 주어진다.

출력
모든 쿼리 적용 후 배열의 최댓값을 정수 한 개로 출력한다 (배열은 0으로 시작하므로 최댓값의 최솟값은 0).

제약
1 ≤ N, Q ≤ 100,000
1 ≤ l ≤ r ≤ N
-109 ≤ v ≤ 109

예시 입력

5 3
1 3 5
2 4 -2
3 5 7

예시 출력

10

설명: 쿼리 적용 과정 — [5,5,5,0,0] → [5,3,3,-2,0] → [5,3,10,5,7]. 최댓값은 10.

정답 및 해설

해설 1. 차분 배열 (Difference Array)

핵심 아이디어
구간 [l, r]에 v를 더하는 연산을 매번 O(r-l+1)로 처리하면 최악 O(NQ) = 1010으로 시간 초과. 차분 배열을 사용하면 각 쿼리당 O(1), 마지막에 누적합 1회(O(N))로 처리 가능.

차분 배열의 정의
원본 배열 A에 대해 diff[i] = A[i] - A[i-1]로 정의. 그러면 구간 더하기 A[l..r] += v는 diff[l] += v; diff[r+1] -= v 두 번의 갱신으로 표현 가능. 배열 복원은 A[i] = diff[1] + diff[2] + ... + diff[i] 누적합.

복잡도
시간: O(N + Q), 공간: O(N)

Python 구현

import sys
input = sys.stdin.readline

def solve():
    N, Q = map(int, input().split())
    diff = [0] * (N + 2)  # 1-indexed, r+1 접근 위해 +2
    for _ in range(Q):
        l, r, v = map(int, input().split())
        diff[l] += v
        diff[r + 1] -= v

    cur = 0
    max_val = 0  # 배열은 0으로 시작하므로 0이 하한
    for i in range(1, N + 1):
        cur += diff[i]
        if cur > max_val:
            max_val = cur
    print(max_val)

solve()

Java 구현

import java.io.*;
import java.util.*;

public class Main {
    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());
        int N = Integer.parseInt(st.nextToken());
        int Q = Integer.parseInt(st.nextToken());
        long[] diff = new long[N + 2];
        for (int i = 0; i < Q; i++) {
            st = new StringTokenizer(br.readLine());
            int l = Integer.parseInt(st.nextToken());
            int r = Integer.parseInt(st.nextToken());
            long v = Long.parseLong(st.nextToken());
            diff[l] += v;
            diff[r + 1] -= v;
        }
        long cur = 0, max = 0;
        for (int i = 1; i <= N; i++) {
            cur += diff[i];
            if (cur > max) max = cur;
        }
        System.out.println(max);
    }
}

다른 접근법
1) Segment Tree with Lazy Propagation: 구간 갱신 + 구간 최댓값을 동적으로 질의할 때 유용. 시간 O((N+Q) log N). 본 문제는 쿼리가 모두 적용된 후에만 결과를 구하므로 오버킬.
2) Sqrt Decomposition: 블록 단위로 lazy 갱신. O((N+Q)√N). 차분 배열 대비 이점 없음.
3) 오프라인 정렬 + 이벤트 스위핑: 시작/종료 이벤트를 정렬해 처리. 본질적으로 차분 배열과 동등.

주의 사항
• 누적값은 long (Java) 또는 Python int(자동 빅인트) 사용 — Q×|v| 최대 ≈ 1014.
• 배열은 0으로 시작하므로 모든 v가 음수여도 최댓값의 하한은 0.
• diff[r+1] 접근 위해 배열 크기 N+2 확보.

해설 2. Copy-on-Write (COW)

면접 답변 구조

① 정의
Copy-on-Write는 메모리 페이지를 즉시 복사하지 않고, 쓰기가 실제로 발생할 때까지 미루는 최적화 기법이다. 부모와 자식 프로세스가 동일한 물리 페이지를 가리키며 페이지 테이블 엔트리를 읽기 전용(Read-only)으로 마킹한다.

② fork() 흐름

  1. 커널이 자식 프로세스의 task_struct, mm_struct를 생성하고 부모의 페이지 테이블을 그대로 복사한다.
  2. 부모·자식 모두 동일한 물리 페이지를 공유하지만 PTE의 RW 비트를 클리어 → 읽기만 가능.
  3. 어느 한쪽이 페이지에 write 시도 → 페이지 폴트(Write Protection Fault) 발생.
  4. 커널이 폴트 핸들러에서 새 물리 페이지 할당 → 내용 복사 → 해당 프로세스의 PTE만 RW로 변경.
  5. 참조 카운트가 1이 되면 이미 단독 소유이므로 복사 없이 RW만 회복.

③ COW가 없을 때의 비용
fork()마다 부모 프로세스의 전체 메모리(수십 MB~GB)를 즉시 복사 → 메모리 대역폭과 시간이 선형 증가. 대부분의 fork()는 직후 exec()로 이미지를 갈아엎으므로 복사한 메모리가 즉시 버려져 낭비된다.

④ 실제 응용 사례

  • Redis BGSAVE / BGREWRITEAOF: 부모는 요청을 계속 처리하고, fork()된 자식이 메모리 스냅샷을 디스크에 기록. 쓰기가 적으면 추가 메모리 부담 최소.
  • fork()+exec() 패턴: 쉘이 외부 명령을 실행할 때 전체 메모리 복사 회피.
  • 유저 공간 COW: mmap(MAP_PRIVATE)로 매핑된 파일 영역에 쓰면 익명 페이지로 복사.

⑤ 키워드 / 후속 질문
PTE, TLB shootdown, vfork()와의 차이, fork bomb, Linux의 /proc/<pid>/smaps에서 Shared_Clean/Dirty, Transparent Huge Page와 COW의 상호작용, Redis에서 큰 페이지 사용 시 COW 비용 증가 문제.

해설 3. Phantom Read / Repeatable Read

면접 답변 구조

① Phantom Read 정의
같은 트랜잭션 안에서 동일한 범위 조건 쿼리를 두 번 실행했을 때, 다른 트랜잭션이 그 사이에 새 행을 INSERT(또는 조건에 부합하도록 UPDATE)하여 결과 집합의 행 수가 달라지는 현상.

② 격리 수준별 발생 여부 (ANSI 표준)
Read Uncommitted, Read Committed, Repeatable Read에서도 발생 가능, Serializable에서 차단.
Repeatable Read는 같은 행을 다시 읽었을 때 같은 값을 보장하지만(Non-repeatable Read 차단), 새 행이 등장하는 것은 막지 않는다.

③ MySQL InnoDB의 예외
InnoDB의 기본 격리 수준 Repeatable Read에서는 Next-Key Lock(레코드 락 + 갭 락)을 사용해 범위 잠금을 걸기 때문에 Phantom Read도 사실상 차단된다. 단, 이는 잠금 읽기(SELECT ... FOR UPDATE, LOCK IN SHARE MODE) 또는 갱신성 쿼리에 한정. 일반 SELECT(consistent read)는 MVCC 스냅샷을 사용해 일관된 뷰를 제공한다.

④ Phantom Read 차단 방법

  1. Serializable 격리 수준 사용 — 트랜잭션을 직렬화하여 모든 이상 현상 차단(성능 비용 큼).
  2. 범위 잠금 / Next-Key Lock: 조건에 포함될 가능성이 있는 인덱스 갭까지 잠근다.
  3. Predicate Lock: PostgreSQL Serializable Snapshot Isolation(SSI)에서 사용. 조건을 추적해 충돌 시 한쪽 트랜잭션 롤백.
  4. 비관적 / 응용 레벨 잠금: 명시적 테이블 잠금, 분산 락(Redis Redlock 등).

⑤ 헷갈리는 포인트
• Non-repeatable Read vs Phantom Read: 전자는 같은 행의 값 변경, 후자는 새 행의 등장.
• InnoDB가 표준과 다르다는 점은 면접에서 자주 묻는 함정.
• MVCC만으로는 갱신 손실(Lost Update)을 막지 못해 SELECT FOR UPDATE 또는 Serializable 필요.

⑥ 키워드 / 후속 질문
Gap Lock, Next-Key Lock, MVCC, Snapshot Isolation, Write Skew, SSI, PostgreSQL Serializable의 false-positive abort, 트랜잭션 격리 수준 변경 명령(SET TRANSACTION ISOLATION LEVEL ...).

해설 4. DNS Cache Poisoning / DNSSEC

① 공격 원리
DNS는 UDP 53번 포트와 16비트 트랜잭션 ID(TXID)만으로 응답을 신뢰한다. 공격자는 캐시 서버가 권한 서버에 질의하는 순간을 노려, 정상 응답보다 먼저 위조 응답을 보내 캐시에 잘못된 매핑(예: bank.com → 공격자 IP)을 저장시킨다. 캐시 TTL 동안 다른 사용자도 악성 사이트로 유도된다.

② Kaminsky 공격 (2008)
존재하지 않는 서브도메인(예: aaa.bank.com, bbb.bank.com, …)을 반복 질의하면서 응답에 Additional 섹션으로 bank.com NS attacker.com 또는 bank.com A 공격자IP를 끼워 넣는다. TXID 16비트(216=65,536)를 brute force로 맞추는 race condition 공격이며, 매번 새 도메인이라 TTL 우회가 가능했던 점이 기존 공격 대비 치명적이었다.

③ DNSSEC 동작

  • DNSKEY: 존(zone)의 공개키 레코드. ZSK(Zone Signing Key)는 RRset 서명, KSK(Key Signing Key)는 DNSKEY RRset 서명.
  • RRSIG: 각 RRset에 대한 디지털 서명. 해시 + 비대칭 서명(RSA/ECDSA).
  • DS (Delegation Signer): 상위 존이 보유하는 자식 존 KSK의 해시. 상위 존이 자식 존 KSK를 인증.
  • Chain of Trust: 루트 KSK(공개) → TLD DS → TLD KSK → 도메인 DS → 도메인 KSK → ZSK → RRSIG → 데이터. 어디든 한 단계라도 깨지면 검증 실패.
  • NSEC / NSEC3: 존재하지 않는 도메인에 대한 인증된 부정 응답.

④ DNSSEC이 제공하는 것 vs 제공하지 않는 것

제공데이터 무결성(Integrity), 출처 인증(Authenticity), 인증된 부정 응답
비제공기밀성(평문 그대로 전송), DoS 방어, 단말~리졸버 구간 보호

⑤ 부가 대응책
• 소스 포트 무작위화(SPR): TXID 16비트 + 소스 포트 ~16비트 ≈ 32비트 엔트로피로 brute force 비용 증가.
• DNS over TLS (DoT) / DNS over HTTPS (DoH): 전송 구간 암호화로 단말~리졸버 도청·변조 방지.
• 0x20 인코딩: 쿼리 도메인의 대소문자를 무작위화하여 추가 엔트로피 확보.

⑥ 헷갈리는 포인트 / 키워드
DNSSEC ≠ 암호화. DNSSEC은 서명만 추가하며 쿼리·응답은 평문 그대로 전송. 기밀성은 DoT/DoH가 담당. KSK/ZSK 분리는 키 회전(rollover)을 용이하게 함. NSEC3은 NSEC의 zone walking 문제를 해시로 완화.

해설 5. XXE (XML External Entity)

① 개념
XML 파서가 외부 엔티티(<!ENTITY ... SYSTEM "...">) 선언을 처리할 때, 공격자가 제어하는 URI를 끼워 넣어 파일 시스템·내부 네트워크·외부 서버에 접근하는 취약점. OWASP Top 10에서 한때 단독 항목, 현재 A04(Insecure Design) / A05(Security Misconfiguration)에 포함.

② 공격 페이로드 예시

<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<foo>&xxe;</foo>

응답에 /etc/passwd 내용이 그대로 노출되거나, 에러 메시지로 유출(out-of-band). Billion Laughs(엔티티 확장 폭발)의 예:

<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
</lol3>

③ 피해 유형 (3가지 이상)

  1. 로컬 파일 읽기: file:/// 스킴으로 서버 내부 파일 유출 (설정 파일, 패스워드 해시, 비밀 키).
  2. SSRF (Server-Side Request Forgery): http://internal-host/로 내부 네트워크 스캔, 클라우드 메타데이터(169.254.169.254) 탈취.
  3. DoS: Billion Laughs / Quadratic Blowup으로 메모리·CPU 고갈.
  4. RCE (드묾): PHP expect:// 또는 Java의 일부 환경에서 발생.
  5. Out-of-Band 데이터 유출: Parameter Entity로 외부 DTD 호출 → 공격자 서버 로그에 데이터 전송.

④ Java 대응 방안 (DocumentBuilderFactory / SAXParserFactory 공통)

DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
// (1) 권장: 안전한 처리 모드
dbf.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
// (2) DTD 자체를 거부 - 가장 안전
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
// (3) 외부 엔티티 비활성화
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
dbf.setFeature("http://apache.org/xml/features/nonvalidating/load-external-dtd", false);
dbf.setXIncludeAware(false);
dbf.setExpandEntityReferences(false);

가능하면 XML 대신 JSON 등 외부 엔티티 개념이 없는 포맷을 사용. SOAP·SAML·XML 기반 RSS/OPML 처리 코드 모두 점검 필요.

⑤ 헷갈리는 포인트 / 키워드
일반 엔티티(General Entity)와 파라미터 엔티티(%name;)를 모두 막아야 함. SYSTEM·PUBLIC 식별자, Blind XXE, OOB-XXE, OWASP XXE Prevention Cheat Sheet, libxml2 XML_PARSE_NOENT·XML_PARSE_DTDLOAD 플래그 주의.

해설 6. 디지털 서명 · 해시 · RSA-PSS

① 메시지가 아닌 해시에 서명하는 이유 (3가지)

  1. 고정 길이 처리 / 성능: RSA 등 공개키 연산은 모듈러스 길이(예: 2048비트)와 같거나 작은 입력만 처리 가능. 임의 길이 메시지를 그대로 서명하면 분할·연쇄 처리가 필요해 비효율적이고 보안 약점이 생긴다. 해시는 임의 길이 → 고정 길이(예: 256비트)로 압축하여 단 1회의 비대칭 연산으로 처리.
  2. 충돌 저항성으로 위변조 방지: 안전한 해시 함수(SHA-256, SHA-3 등)는 충돌·역상 저항성을 가지므로, 같은 해시를 갖는 다른 메시지를 만들 수 없다. 따라서 해시에 대한 서명이 곧 메시지 무결성 보장.
  3. 구조적 공격 회피: 메시지 자체를 서명하면 RSA의 곱셈 동형성(homomorphism) 등으로 인한 기존 서명 재사용·위조 공격에 노출. 해시(특히 random oracle 모델)로 입력을 무작위화하면 이런 대수적 구조 공격이 차단된다.

(부가 이점: 짧은 해시만 별도 보관·전송 가능, 표준화된 OID로 알고리즘 식별 용이)

② PKCS#1 v1.5 vs RSA-PSS

구분PKCS#1 v1.5RSA-PSS (PKCS#1 v2.1+)

③ RSA-PSS 동작 요약
EMSA-PSS 인코딩: H' = Hash(0x00||0x00||0x00||0x00||0x00||0x00||0x00||0x00 || Hash(M) || salt), 이어 DB = padding||0x01||salt를 MGF1로 마스킹 후 H'와 결합 → RSA 비공개 지수로 서명. 검증은 역으로 마스크 해제 후 H' 재계산하여 비교.

④ 헷갈리는 포인트 / 키워드
• PSS의 결정성 부재가 보안적 약점이 아니라 오히려 강점(메시지-서명 매칭이 노출 안 됨).
• 결정적이지만 표준화된 결정적 서명이 필요한 환경(블록체인, 결정적 빌드)에서는 EdDSA(Ed25519)를 채택하는 경향.
• 키워드: EMSA-PSS, MGF1, salt length(보통 hash와 동일), Random Oracle Model, Full Domain Hash(FDH), RSASSA-PSS, OAEP(암호화용 — 서명과 혼동 주의), TLS 1.3 signature_algorithms.
