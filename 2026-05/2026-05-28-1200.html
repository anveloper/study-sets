문제 1. Trie 기반 자동완성 사전

난이도: 중Trie

다음 두 연산을 지원하는 자동완성 사전을 구현하라.

  • insert(word: str) — 단어를 사전에 추가
  • suggest(prefix: str, k: int) -> List[str] — 해당 prefix로 시작하는 단어 중 사전순으로 앞선 최대 k개를 반환

제약: 단어는 소문자 영어, 최대 50자. insert는 O(L), suggest는 O(L + 결과 길이의 합) 안에 동작해야 한다.

예시:

d = Autocomplete()
d.insert("apple"); d.insert("apply"); d.insert("apricot"); d.insert("banana")
d.suggest("ap", 5)   # → ["apple", "apply", "apricot"]
d.suggest("app", 1)  # → ["apple"]

문제 1 해설 — Trie 자동완성

핵심 아이디어: 문자 단위 트리(Trie)를 사용해 prefix 검색을 O(L)에 수행. 각 노드는 자식 사전과 단어 종료 플래그를 가진다. suggest는 prefix 노드까지 따라간 뒤 DFS로 사전순(소문자 a~z) 탐색하며 k개 모이면 조기 종료.

시간 복잡도: insert O(L), suggest O(L + 결과 단어 길이 합)
공간 복잡도: O(전체 문자 수)

class TrieNode:
    __slots__ = ('children', 'is_end')
    def __init__(self):
        self.children = {}   # char → TrieNode
        self.is_end = False


class Autocomplete:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word: str) -> None:
        node = self.root
        for ch in word:
            if ch not in node.children:
                node.children[ch] = TrieNode()
            node = node.children[ch]
        node.is_end = True

    def suggest(self, prefix: str, k: int):
        # 1) prefix 노드까지 이동
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return []
            node = node.children[ch]
        # 2) DFS 사전순, k개 수집
        results = []
        def dfs(cur, path):
            if len(results) >= k:
                return
            if cur.is_end:
                results.append(prefix + path)
                if len(results) >= k:
                    return
            for ch in sorted(cur.children.keys()):
                dfs(cur.children[ch], path + ch)
        dfs(node, "")
        return results


# 테스트
d = Autocomplete()
for w in ["apple", "apply", "apricot", "banana"]:
    d.insert(w)
print(d.suggest("ap", 5))   # ['apple', 'apply', 'apricot']
print(d.suggest("app", 1))  # ['apple']

다른 접근: 단순 정렬된 배열 + binary search로 prefix 시작 위치 찾기도 O(log N · L)이지만, 동적 삽입과 부분 prefix 탐색이 잦으면 Trie가 압도적. 메모리가 문제면 Compressed Trie(라딕스 트리) 사용 가능.

문제 2 해설 — 격리 수준과 Phantom Read

4가지 격리 수준과 허용 이상 현상:

격리 수준Dirty ReadNon-Repeatable ReadPhantom Read
READ UNCOMMITTEDOOO
READ COMMITTEDXOO
REPEATABLE READXXO (표준) / X (InnoDB)
SERIALIZABLEXXX

이상 현상 정의:

  • Dirty Read: 커밋 안 된 변경을 다른 트랜잭션이 읽음
  • Non-Repeatable Read: 같은 행을 두 번 읽었는데 값이 다름 (사이에 다른 TX가 UPDATE/DELETE 커밋)
  • Phantom Read: 같은 조건의 범위 쿼리를 두 번 했는데 결과 행 개수가 달라짐 (사이에 INSERT 커밋)

MySQL InnoDB의 Phantom Read 방지:

  1. Consistent Read (일반 SELECT): MVCC로 트랜잭션 시작 시점의 스냅샷을 읽음 → 같은 범위 쿼리는 같은 결과 → Phantom 없음.
  2. Locking Read (SELECT ... FOR UPDATE/SHARE, INSERT/UPDATE): MVCC로는 부족 (다른 TX의 INSERT 시점에 락이 없음). InnoDB는 Next-Key Lock을 잡음 — 인덱스 레코드 + 직전 갭(gap)을 함께 잠금. 새 INSERT가 그 범위에 들어오려면 갭락 대기 → Phantom 발생 불가.

주의: InnoDB REPEATABLE READ에서도 일반 SELECT는 스냅샷, FOR UPDATE는 락. 같은 트랜잭션에서 두 방식을 섞으면 결과가 다를 수 있음 (소위 "phantom의 부분 회피").

문제 3 해설 — HTTP/3와 QUIC

TCP HOL Blocking 문제: HTTP/2는 단일 TCP 연결에서 여러 스트림을 다중화. 하지만 TCP는 패킷 손실 시 해당 세그먼트 이후의 모든 데이터를 재전송될 때까지 상위 계층에 전달하지 않음 → 한 스트림의 패킷 손실이 모든 스트림을 멈춤. HTTP/2 레벨의 다중화 이점이 TCP 레벨에서 무력화.

QUIC의 해결: QUIC은 UDP 위에서 동작하며, 각 스트림이 독립적인 신뢰성과 순서 보장을 가짐. 한 스트림의 패킷 손실은 그 스트림만 멈추고 다른 스트림은 계속 처리됨. 또한 QUIC은 전송 + 암호화를 통합 (TLS 1.3 핸드셰이크가 QUIC 핸드셰이크 안에 포함).

0-RTT 재개: 이전 연결에서 협상한 키 자료를 사용해, 첫 패킷에 애플리케이션 데이터를 함께 보냄. RTT 0번 = 핸드셰이크 왕복 없이 즉시 통신.

  • 보안 고려사항: 0-RTT 데이터는 replay attack에 취약 — 공격자가 캡처한 0-RTT 패킷을 재전송하면 서버가 같은 요청을 두 번 처리할 수 있음. 따라서 멱등(idempotent) 요청에만 허용해야 함 (GET은 OK, POST는 위험).

Connection Migration: QUIC 연결은 IP/Port 기반이 아닌 Connection ID 기반. 클라이언트가 Wi-Fi → 셀룰러로 네트워크 전환해도 같은 Connection ID를 사용해 연결 유지 (TCP는 새 연결 필요).

  • 보안 고려사항: 마이그레이션 시 경로 검증(Path Validation) 필수 — 새 경로가 진짜 같은 클라이언트인지 PATH_CHALLENGE/PATH_RESPONSE로 확인. NAT rebinding을 통한 DoS 가능성도 고려.

문제 4 해설 — SSRF + AWS IMDS

(1) IMDSv1 악용 URL:

GET http://169.254.169.254/latest/meta-data/iam/security-credentials/
→ 인스턴스에 붙은 IAM 역할 이름 목록

GET http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>
→ 임시 자격증명 (AccessKeyId, SecretAccessKey, Token, Expiration)
→ 이 자격으로 AWS CLI/SDK로 S3, RDS, IAM 등 접근 가능

(2) IMDSv2의 차단 방식: 토큰 기반 세션 인증.

  1. 클라이언트가 먼저 PUT /latest/api/token로 토큰 발급 요청 (X-aws-ec2-metadata-token-ttl-seconds 헤더 필요).
  2. 응답으로 받은 토큰을 이후 모든 메타데이터 요청에 X-aws-ec2-metadata-token 헤더로 첨부.
  3. 대부분의 SSRF는 단순 GET만 가능 → PUT으로 토큰 발급 못 함 → 메타데이터 접근 차단.
  4. 추가 안전장치: X-Forwarded-For 헤더가 있는 요청은 거부, hop limit 1 (호스트 외부로 토큰 유출 방지).

(3) SSRF 필터 우회 기법 예시:

  • DNS Rebinding: 공격자 통제 도메인이 처음엔 정상 IP를 반환 → 검증 통과 → 짧은 TTL 만료 후 169.254.169.254 반환 → 실제 요청은 메타데이터 서비스로
  • IP 표기 우회: http://0177.0.0.1/ (8진수), http://2130706433/ (10진수), http://[::ffff:169.254.169.254]/ (IPv6-mapped IPv4)
  • URL 파서 차이: http://evil.com#@169.254.169.254/ — 일부 파서는 evil.com을 호스트로, 다른 파서는 169.254.169.254로 해석
  • 리다이렉트: 허용된 외부 URL이 302로 내부 IP로 리다이렉트

문제 5 해설 — 블록 암호 운영 모드

ECB (Electronic Codebook): 평문을 블록 단위로 나눠 각각 독립 암호화. 같은 평문 블록 → 같은 암호문 블록.
문제점: 패턴이 그대로 누출. 유명한 "ECB 펭귄" 이미지 — 픽셀 데이터를 ECB로 암호화해도 펭귄 윤곽이 보임. 어떤 보안 용도에도 부적절.

CBC (Cipher Block Chaining): 이전 암호문 블록과 XOR 후 암호화. IV 필요.
요구사항: IV는 예측 불가능(unpredictable)해야 함 — TLS 1.0의 IV 예측 가능성이 BEAST 공격으로 이어졌음.
패딩 오라클 공격: 서버가 PKCS#7 패딩 오류 여부를 응답으로 흘리면, 공격자는 1바이트씩 평문 복호화 가능 (Vaudenay 2002, POODLE).

CTR (Counter): 카운터(nonce || counter)를 암호화한 키 스트림과 평문을 XOR. 스트림 암호처럼 동작.
장점: 블록 간 의존성 없음 → 완전 병렬 처리 가능 (암·복호화 모두). 임의 위치 접근(random access)도 가능.
주의: nonce 재사용 금지 — 같은 nonce·키 조합으로 두 평문 암호화하면 두 암호문 XOR이 두 평문 XOR과 같아져 복호화 가능.

GCM (Galois/Counter Mode): CTR로 암호화 + GMAC으로 인증 → AEAD(Authenticated Encryption with Associated Data).
병렬화: CTR 부분은 완전 병렬, GMAC도 GF(2^128) Galois 곱셈이 병렬화 가능. 하드웨어 가속(AES-NI, PCLMULQDQ) 지원으로 매우 빠름.

TLS 1.3가 AEAD만 허용하는 이유:

  • CBC + HMAC 조합의 "MAC-then-Encrypt"는 Lucky13, padding oracle 등 구조적 취약점 누적
  • AEAD는 암호화·인증을 단일 알고리즘으로 결합 → 잘못 사용할 가능성 감소
  • TLS 1.3은 GCM, ChaCha20-Poly1305, CCM만 허용. RC4, 3DES, CBC 모드 전부 제거.

키워드: Nonce reuse, AEAD, AES-NI, ChaCha20-Poly1305(모바일 친화), Forward Secrecy.

문제 6 해설 — RFC 3227 휘발성 순서

휘발성 순서 (높음 → 낮음) 및 Linux 도구:

  1. CPU 레지스터, 캐시 — 일반적 도구로는 수집 불가. 메모리 덤프 시점에 일부 캡처될 수 있음.
  2. 라우팅 테이블, ARP 캐시, 프로세스 테이블, 커널 통계, 메모리 매핑
    • ip route / netstat -rn
    • ip neigh / arp -an
    • ps auxf, ls -la /proc/[PID]/
    • ss -tunap (열린 소켓·포트·연결 상태)
  3. 물리 메모리 (RAM) 덤프
    • LiME (Linux Memory Extractor) 커널 모듈
    • AVML (Microsoft)
    • 이후 Volatility / Rekall로 분석
  4. 임시 파일 시스템 — /tmp, /var/tmp, /dev/shm tar로 보존
  5. 디스크 / 영구 매체 — dd, dcfldd, dc3dd로 비트 단위 이미징
  6. 원격 로그·모니터링 데이터 — SIEM, syslog 서버, 방화벽 로그
  7. 물리적 구성, 토폴로지, 백업 매체

무결성 보장 필수 절차:

  1. 해시 즉시 계산 및 보관: 수집 직후 sha256sum으로 해시 산출, 별도 매체에 기록. 분석 시점 해시와 비교해 변조 없음 입증.
  2. Chain of Custody 문서화: 누가·언제·어디서·어떻게 수집했고, 이후 누구에게 인계됐는지 시간 순으로 기록. 법적 증거 능력의 핵심.
  3. Write Blocker 사용: 디스크 이미징 시 하드웨어/소프트웨어 write blocker로 원본을 절대 변경하지 않음. 분석은 사본에서만 수행.

추가 키워드: Live Response, Triage, Memory Forensics(Volatility), 디지털 증거의 4원칙(동일성·무결성·정당성·재현성), 사고대응팀(CSIRT).
